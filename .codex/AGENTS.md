# Global AGENTS.md（Codex 全プロジェクト共通指示）

## 言語

- **回答・説明・エラー対応・PR 本文・Issue 本文**: 日本語
- **コード・コード内コメント・PR タイトル・commit メッセージ**: 英語
- 固有名詞・ファイルパス・環境変数名は原文（英語）表記を保持する

## ユーザーのコミュニケーションスタイル

ユーザーは短い命令形（「〜して」「〜で」）で指示する。文脈は直前の作業・現在のブランチ・オープン中の PR から補完すること。不明なら着手前に 1 回だけ確認する。

### 省略語彙集

| 表現 | 意味 |
| --- | --- |
| 「local cleanup」 | local main を最新化し、マージ済みの不要ブランチと worktree を削除する |
| 「積んで」「PR に積んで」 | 現在オープン中の PR に commit を追加して push する |
| 「続けて」「再開」 | 直前に中断したタスクをそのまま継続する |
| 「〜した?」「できてますか?」 | 検証結果の提示要求。yes/no ではなく、実行ログ・diff・テスト結果など証拠を添えて答える |
| 「ワンライナーで」 | コピー&ペーストで実行できる 1 行のコマンドを提示する |

## コア原則

- **シンプル第一**: すべての変更をできる限りシンプルにする。影響するコードを最小限にする
- **手を抜かない**: 根本原因を見つける。一時的な修正・表面的な対処は避ける。シニアエンジニアの水準を保つ
- **影響を最小化する**: 変更は必要な箇所のみにとどめる。バグを新たに引き込まない

## 指示の階層

- 作業対象が `$HOME/dev/me/` 配下なら、最初に `$HOME/dev/me/AGENTS.md` を読む
- 作業対象が `$HOME/go/src/github.com/awa/` 配下なら、最初に `$HOME/go/src/github.com/awa/AGENTS.md` も読む
- リポジトリや下位ディレクトリの `AGENTS.md` / `CLAUDE.md` は、より具体的な指示として優先する
- 共通指示に手順を増やしすぎず、反復可能な複数手順は skill、機械的処理は script、外部システム接続は MCP に分離する

## コンテキスト効率

- 調査は `rg --files`、対象を絞った `rg`、必要箇所の部分読み込みの順で進める。巨大ファイル、ログ、検索結果を無条件に全件読み込まない
- 既に得た事実を再取得せず、追加調査では未確定事項だけを確認する
- 大量の探索結果やログを伴う調査はサブエージェントへ隔離し、返却は結論、根拠、未確定事項、検証結果に限定する
- 圧縮ツールや新しい知識形式は、代表タスクで品質、入力 token、所要時間を比較してから導入する。公称削減率だけで採用しない
- compaction や引き継ぎでは、目的、確定事項、却下案、変更ファイル、検証結果、未完了事項、次の一手を保持する
- ユーザーの修正は、再発した不変的なパターンだけを最も狭い有効範囲の指示へ反映する。タスクごとの一時的な学びを新規ファイルへ自動保存しない

## サブエージェント委譲方針

### 基本方針

- メインエージェントは、要件解釈、成功条件の確定、設計判断、委譲、結果統合、最終判断、ユーザー対応を担う
- 小さな単発作業は委譲せず、メインエージェントが直接処理してよい
- サブエージェントは別のサブエージェントを起動しない
- 各サブエージェントの報告は、結論、根拠、未確定事項、検証結果だけに絞る

### researcher

- 実装前のコードベース調査、影響範囲確認、仕様確認、根拠収集に使用する
- 調査対象と確認事項が独立している場合のみ、複数の読み取り専用タスクを並列化できる
- ファイル変更を許可しない

### implementer

- 成功条件、実装方針、対象ファイルが確定した後に使用する
- 同時に動かす書き込み担当は 1 体だけとする
- 対象ファイル、禁止事項、検証コマンドを委譲時に明示する
- 実装中に設計変更が必要になった場合は、独自判断で範囲を広げずメインへ戻す

### reviewer

- 非自明な実装が完了した後に使用する
- 原則として差分と関連ファイルだけを確認する
- レビュー対象を編集させない
- 指摘がある場合は、メインが採否を判断してから implementer に修正を戻す

### 並列実行

- 複数エージェントに同じファイルを並行編集させない
- 並列化は、独立した読み取り、調査、ログ解析に限定する
- researcher、implementer、reviewer の工程は原則として直列に実行する

### フォールバック

- モデル未提供、起動失敗、権限不足が発生した場合、同じ委譲を反復しない
- 失敗理由、完了済み作業、未完了事項をメインへ戻す
- Luna が利用できない場合は Terra、Terra も利用できない場合は親モデル継承を使用する

### 高リスク作業

認証、権限、課金、個人情報、データ移行、破壊的操作、本番基盤の変更は、メインエージェントが直接判断する。
通常の reviewer だけでは不十分な実績が確認された場合に限り、Sol を使用する critical_reviewer の追加を検討する。

### Claude CLI

- Codex のサブエージェントを標準とし、ユーザーが Claude を指定した場合、Claude 固有の挙動確認、独立したセカンドオピニオンが有効な場合に Claude CLI を使用する
- Claude の呼び出しには `~/.codex/skills/github-pr-cleanup/scripts/claude_worktree_session.sh --agent <role> [--model sonnet|opus] --cwd <worktreeの絶対パス> -- <prompt>` を使用する。`claude` を単発で直接起動しない
- Claude セッションは worktree 単位で 1 つだけ管理する。ラッパーが初回の `--session-id` と、2 回目以降の `--resume` を自動的に切り替える
- 新しい worktree では新規セッションを開始し、別 worktree のセッションを resume しない。role を変更しても同じ worktree の文脈を継続する
- Claude のモデルは原則 `sonnet` を使用する。重要な監査、重大な設計判断、複雑で抽象度の高いレビューでは `--model opus` を明示する
- Codex と Claude の再帰呼び出しを防ぐため、ラッパーは `--strict-mcp-config` と空の MCP 設定を常に指定する
- 読み取り専用の調査・レビューは `researcher` / `reviewer`、書き込みは `implementer` を指定する。書き込みを許可する場合も、同じファイルを Codex や別エージェントと並行編集させない
- Claude 実行中は同じ worktree のセッションを並行起動しない。ラッパーの lock エラーを無視しない
- local cleanup では worktree を削除する前に、その worktree に紐づく Claude セッションと管理情報を専用 cleanup スクリプトで削除する

## スコープ復唱（変更着手前）

- 変更に着手する前に、対象のファイルパス・ページパスを明示して認識を合わせる
- 類似ターゲットが複数存在する場合（例: 複数サービスの contact ページ、同名ファイル）は、推測で進めず着手前に対象を確認する
- 指示と実際の対象が食い違っていたら、作業を進める前に指摘する

## Git 規約

### commit メッセージ

Conventional Commits 形式: `<type>(<scope>): <description>`

- type: `feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` / `build` / `ci` / `chore`
- 破壊的変更は `!` を付与（例: `feat!: remove deprecated API`）
- commit は意味のある粒度でまとめる（機械的な一括 commit にしない）
- **Issue 番号は commit に紐づけない**（PR に紐づける）

### ブランチ・worktree

- コード変更を伴う作業は専用ブランチ + 専用 worktree で開始する（軽微な修正・既存 PR への追記は例外）
- worktree はプロジェクト内の `.worktrees/<branch-name>` に作成する: `git worktree add .worktrees/<branch-name> -b <branch-name>`
- `.worktrees/` が `.gitignore` に未追加なら追加する
- **worktree 作成直後に絶対パスで cd する**。シェルの cwd は親リポジトリに残るため、cd せずに grep / test / git を実行すると親側のクリーンなファイルを読んでしまう

### push・PR

- push 前に必ず `git fetch --all && git rebase origin/main`（デフォルトブランチ名に読み替え）を実行する
- PR タイトルは Conventional Commits 形式の英語、本文は日本語
- PR には可能な限り Issue を紐づける（例: `- #123`）
- 特に指定がない場合 draft で作成し、GitHub Copilot をレビュワーに追加する
- 1 PR につき 1 つの目的に集中する
- リポジトリに `PULL_REQUEST_TEMPLATE.md` があればそれに従う

### マージ後 cleanup（自発的に実施）

PR がマージされたら、指示を待たずに次を実施して結果を報告する:

1. local main（デフォルトブランチ）を最新化
2. マージ済みブランチを削除
3. 対応する worktree の Claude セッションを削除
4. 対応する worktree を削除

## 長時間タスクの進捗報告

- 多数の項目を処理するタスクは、チャンク単位（例: 10 件ごと）に commit & push し、進捗を報告する
- 処理が継続しているか・止まっているかをユーザーに質問させない。節目ごとに「N/M 件完了」を自発的に伝える
- 中断・再開できる設計にする（処理済みリストや manifest を残す）

## 完了報告の基準

- 動作を証明できるまで「完了」と言わない。テスト実行結果・ログ・実際の表示確認を添える
- オフラインテスト（fake / httptest 等）が通っても、可能なら live の実データで 1 回検証する
- 対応できない要件は silent に落とさず「unsupported」と明示する

## Markdown

- Markdown ファイルの編集後は `npx markdownlint-cli2 --config ~/dev/me/dotfiles/.markdownlint.yaml <file>` を実行し、警告があれば修正する

## シェル

- `echo "---"` のようなダッシュ始まりのクォート文字列は避け、`echo '~~~'` 等を使用する
