# 文脈の効率 — 測った内訳と、却下した案

結論は `CLAUDE.md` にある。ここはその根拠。

## 測ったこと

セッション 1 本（道具を使った往復 6,997 回・入力 72 億トークン）。

| 測ったこと | 値 |
| --- | --- |
| 入力に占める**これまでの会話の読み直し** | **97.3%** |
| こちらが書いた量 対 返ってきた量 | **49.1% 対 35.6%** |
| 1 依頼あたりの呼び出し | 中央値 **8 件** |

**会話は縮まない。** 一度入れたものは以後すべての往復で読み直される。
だから 1 回を軽くするより、そもそも入れない方が効く。

## 却下した 3 案

| 案 | 実測 | 判断 |
| --- | --- | --- |
| 大きい出力を減らす | 上位 1% を全部消しても出力量の **13%** | 効かない |
| 同じ命令の再実行を避ける | **0.4%** | 効かない |
| **入力を圧縮する道具**を入れる | 対象は会話の **15.6%**・提供元の実運用中央値 **4.8%** | **採用しない** |

圧縮が効かない理由は、**最大の項目がこちらの書いた指示**（49.1%）で、
圧縮は「読むもの」しか縮めないため。

## まとめて呼ぶことについて

**1 回の呼び出しに複数の命令をまとめるのは既にできている。**
区切り記号を含む呼び出しが **79.8%**・中央値 2 つ。

**本当に 1 命令だけなのは 8.3%** で、その中身は単発で完結する確認。
まとめる相手がいないので、ここは追わない。

## 2026-09-20 の失敗

「まとめた回数ゼロ」という測定を根拠に仕組みを作り、PR を出し、外部レビューまで通したが、
**測り方が誤っていた**（1 応答あたりの道具の数だけを見て、1 呼び出しに詰めた命令の数を
見ていなかった）。

**矛盾は既に手元のデータにあった**——自分のコマンドが `;` と `&&` だらけである、という形で。

外部レビューは前提を検査しない。根拠の数字を添えて渡すと、その上に乗った設計だけを見る。
18 件の指摘はすべて仕組みの設計に向き、**数字そのものには誰も触れなかった**。
