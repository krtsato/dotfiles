# 文脈の効率 — 測った内訳と、見送った案

結論は `CLAUDE.md` の「文脈に入れたものは、毎回もう一度読まれる」にある。ここはその根拠。

**測ったのは 1 セッションだけ**（2026-09-20・約 7,000 回の道具呼び出しを含む長時間の作業）。
他のセッションで同じ割合になる保証はない。数字を使う前に、下の「測り方」で測り直すこと。

## 仕組み

応答を 1 回返すたびに、それまでの会話**全体**がモデルへ送り直される。
会話から何かが消えることはないので、**1 回の道具呼び出しで読み込んだ出力は、
そのセッションが続くかぎり毎回送られ続ける**。

だから費用を決めるのは 1 回の重さではなく、**入れたものの量 × 残りの往復回数**。
同じ 10KB でも、セッションの最初に入れたものと最後に入れたものでは費用が桁で違う。

**サブエージェントが効く理由も同じ**。向こうが読んだ出力はこちらの会話に入らない。
戻ってくるのは報告の数行だけなので、以後の往復で送り直されるのもその数行だけ。

## 何にトークンを使っていたか

送った入力の内訳。会話が長くなるほど、同じ内容を何度も送り直すことになる。

| 内訳 | 割合 | 意味 |
| --- | --- | --- |
| **送り直した分** | **97.3%** | 以前の往復で既に送った内容を、また送っている |
| 新しく足した分 | 2.7% | その往復で新たに増えた内容 |

**会話の本文**（道具の入出力と発言）を種類別に分けると次のとおり。合計 100%。

| 種類 | 割合 |
| --- | --- |
| **こちらが書いた道具への指示** | **49.1%** |
| 道具から返ってきた出力 | 35.6% |
| こちらの発言 | 8.9% |
| 依頼の文章 | 6.4% |

**最大の項目は「返ってきたもの」ではなく「こちらが書いたもの」**。
この事実が、下の 3 案の評価を分けた。

## 検討して見送った 3 案

いずれも「効かない」と判断した。**前提が変われば結論も変わる**ので、再検討の条件を添える。

### 1. 大きい出力を減らす

呼び出し 1 回あたりの出力は**中央値 274 バイト**。大物がいない。

| 上位 | その分が出力全体に占める割合 |
| --- | --- |
| 1% | **13%** |
| 5% | 34% |

上位 1% を完全に無くしても 13% しか減らない。**費用は約 6,000 件の小さな呼び出しに分散**している。

**再検討する条件**: 1 回の出力の中央値が桁で増えたとき。

### 2. 同じ命令の再実行を避ける

6,184 回のうち、**文字列が完全に一致する再実行は 26 回（0.4%・7KB）**。ほぼ起きていない。

**再検討する条件**: 同じ調査を毎日繰り返す運用（定期点検・監視）が主になったとき。

### 3. 入力を圧縮する道具を入れる

評価した道具は **Headroom**（`headroom-ai`）。道具の出力をモデルに渡す前に圧縮し、
必要なら元を取り直させる仕組み。手元で動き、外部サービスへは送らない。

| 見たこと | 値 |
| --- | --- |
| 公称の削減率（JSON やログの例） | 83〜93% |
| **提供元が公表する実運用の中央値** | **4.8%** |
| このセッションで圧縮対象になりうる割合 | **15.6%** |

15.6% は「返ってきた出力 35.6%」×「そのうち圧縮が効く形（ログ・表・JSON）43.7%」。
仮に対象を 8 割圧縮できても**全体で 12.4% が上限**。

**最大の項目（こちらが書いた指示 49.1%）には触れない。** 圧縮するのは読むものだけのため。
また、公式に「コード解析は意図的に圧縮しない」と明記されている。

**再検討する条件**:

- 返ってきた出力が、こちらの書く量を明確に上回るようになったとき
- その出力に占めるログ・表・JSON の割合が大きく増えたとき
- 圧縮する側が「書いた指示」も対象にするようになったとき

## まとめて呼ぶことについて

往復を減らす方法は 2 通りある。**片方しか数えないと読み違える**（下の失敗を参照）。

| 方法 | このセッションでの実績 |
| --- | --- |
| 1 応答に道具を複数並べる | **0 回** |
| **1 回の呼び出しに命令を複数詰める** | **79.8%**（区切り記号の数は中央値 2 つ） |

**本当に 1 命令だけなのは 8.3%**（514 件）。中身は `find` や `gh issue view` のような
単発で完結する確認で、まとめる相手がいない。**ここは追わない。**

## 2026-09-20 の失敗

前半の数字だけを見て「独立した呼び出しを 1 度もまとめていない」と判断し、
それを根拠に hook を作り、PR を出し、外部レビュー（18 件の指摘）まで通した。
**測り方が誤っていた。**

- 数えていたのは「1 応答あたりの道具の数」だけで、**1 呼び出しに詰めた命令の数を見ていなかった**
- **矛盾は既に手元のデータにあった**——自分のコマンドが `;` と `&&` だらけである、という形で
- 18 件の指摘はすべて hook の設計に向き、**前提の数字には誰も触れなかった**

hook は取り下げた。ここから得た規律は `CLAUDE.md` の「数字を根拠に決めるとき」にある。

## 読み違えないための 2 つの問い

`CLAUDE.md` の「数字を根拠に決めるとき」の表は、次の 2 つを短くしたもの。

### その数字が本当なら、他に何が成り立つはずか

同じやり方で測り直しても同じ答えしか出ない。**別の角度から見て辻褄が合うか**を見る。

> 「独立した道具呼び出しを 1 度もまとめていない」と測れた。
> もし本当なら、自分が書いたコマンドは 1 つの用途しか持たないはず。
> 実際は `;` と `&&` で複数の命令が繋がっていた。**測り方が間違っていた。**

### その動詞は何通りの形で起きるか

> 「まとめる」には 2 通りある。**1 応答に道具を複数並べる**のと、
> **1 回の呼び出しに命令を複数詰める**の。
> 片方しか数えないと、できていることを「できていない」と読み違える。

## 測り方

セッションの記録（`~/.claude/projects/<プロジェクト>/<セッション>.jsonl`）を読む。
1 行が 1 レコードの JSON で、`message.role` と `message.content[].type` で種類が分かる。

| 知りたいこと | 見る場所 |
| --- | --- |
| 送り直した割合 | `message.usage` の `cache_read_input_tokens` と `cache_creation_input_tokens` |
| 本文の内訳 | `content[]` の `tool_use`（書いた指示）と `tool_result`（返った出力）の文字数 |
| 1 応答あたりの道具の数 | 1 レコード内の `tool_use` の個数 |
| 1 呼び出しの命令の数 | `tool_use.input.command` に含まれる `;` と `&&` の数 |

**最後の 1 行を省くと、2026-09-20 と同じ読み違えをする。**
