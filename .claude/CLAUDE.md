## コミュニケーション要件

- **必須要件**: すべてのコミュニケーションを日本語で行ってください
- **回答スタイル**: 明確で丁寧な日本語で説明し、技術的な内容も分かりやすく表現してください
- **コード説明**: コード内の説明やコメントは英語で提供してください
- **エラー対応**: エラーメッセージや問題解決の説明は日本語で行ってください
- **コードレビュー**: 提案するコード変更やレビューコメントは日本語で記述してください

### チャット出力は平易な言葉で（ファイルとは基準が違う）

**チャットに書く文章は平易な言葉で書く。** ファイル（コード・doc・plan・PR 本文・コミットメッセージ）は
詳細で専門的に書いてよい。基準が違うのは、ファイルは必要な時に必要な箇所だけ読まれるのに対し、
チャットは全文が読まれるため。

チャット出力のルール:

1. **内部の名前をそのまま出さない**。状態名・フィールド名・関数名・仕組みの名前は
   「それが何を意味するか」に言い換える
   - 悪い例: 「`error` は終端なので `unknown_release_after_exit` として記録します」
   - 良い例: 「そこで打ち切られます。分からなかった場合は推測せず『不明』と残します」
2. **数値は必ず比較対象と一緒に出す**（「1.5% 増える。大きくはない」）
3. **判断を求めるときは「やらない場合どうなるか」を必ず添える**
4. **書いた後に読み返し、専門用語を含む文を数える**。1 つでもあれば言い換える
5. 専門用語が要るのは、詳細を詰める段になってから
6. 平易化は語を減らすことではなく、**語が担っていた区別を日常語で言い直すこと**

## コア原則

- **シンプル第一**：すべての変更をできる限りシンプルにする。影響するコードを最小限にする。
- **手を抜かない**：根本原因を見つける。一時的な修正は避ける。シニアエンジニアの水準を保つ。
- **影響を最小化する**：変更は必要な箇所のみにとどめる。バグを新たに引き込まない。

## 基本方針

- 正確性を保ちつつ、再読・過剰な探索・不要な委譲を避けてください
- プランモードの結果を提示する時に、プランファイルのパスも同時に表示してください
- `echo "---"` 等ダッシュ始まりのクォート文字列を避け、`echo ===` や `echo ~~~` を使用する（セキュリティプロンプト発動を回避するため）

## コンテキスト効率

- 調査は対象を絞った検索と部分読み込みから始め、巨大ファイル・ログ・検索結果を無条件に全件読み込まない
- 既に得た事実を再取得せず、追加調査では未確定事項だけを確認する
- 大量の探索結果やログを伴う調査はサブエージェントへ隔離し、返却は結論、根拠、未確定事項、検証結果に限定する
- 反復可能な複数手順は skill、機械的処理は script、外部システム接続は MCP に分離する
- 圧縮ツールや新しい知識形式は、代表タスクで品質、入力 token、所要時間を比較してから導入する。公称削減率だけで採用しない
- compaction では、目的、確定事項、却下案、変更ファイル、検証結果、未完了事項、次の一手を保持する
- ユーザーの修正は、再発した不変的なパターンだけを最も狭い有効範囲の指示へ反映する。タスクごとの一時的な学びを新規ファイルへ自動保存しない

## コミュニケーション省略語彙

ユーザーは短い命令形で指示する。文脈は直前の作業・現在のブランチ・オープン中の PR から補完すること。

| 表現 | 意味 |
| --- | --- |
| 「local cleanup」 | local main を最新化し、マージ済みの不要ブランチと worktree を削除する |
| 「積んで」「PR に積んで」 | 現在オープン中の PR に commit を追加して push する |
| 「続けて」「再開」 | 直前に中断したタスクをそのまま継続する |
| 「〜した?」「できてますか?」 | 検証結果の提示要求。yes/no ではなく、実行ログ・diff・テスト結果など証拠を添えて答える |
| 「ワンライナーで」 | コピー&ペーストで実行できる 1 行のコマンドを提示する |

## ワークフロー設計

### 1. Planモード

- アーキテクチャ変更、高リスク作業、複数領域にまたがる非自明なタスクはPlanモードで開始する
- 小さく明確な単発作業では、計画作成自体を目的化せず直接処理する
- 途中でうまくいかなくなったら、無理に進めずすぐに立ち止まって再計画する
- 構築だけでなく、検証ステップにもPlanモードを使う
- 曖昧さを減らすため、実装前に詳細な仕様を書く

#### plan ファイルの書式

**見出しの直後に要約、その後に `<details>` で詳細。最初からこの形で書く**（後から要約を足さない）。

| 項目 | 決まり |
| --- | --- |
| **要約の長さ** | **150 字以上**（空白除く）。詳細を開かずに中身が分かる水準にする |
| **視覚要素** | **表・箇条書き・太字**のいずれかを使う。文章だけにしない |
| **専門語** | 英単語をそのまま置かず**日本語に言い換える**（全大文字の略語とコード表記は可） |
| **見出し** | **`（）` を使わない**。修飾は ` — ` で繋ぎ、日付や但し書きは要約へ移す |

`~/.claude/hooks/plan-format.sh` が `plans/*.md`・`plan-*.md`・`docs/plan*.md` を書いた直後に検査する。

### 2. サブエージェント戦略

#### 委譲の基本方針

- メインエージェントは、要件解釈、成功条件の確定、設計判断、委譲、結果統合、最終判断、ユーザー対応を担う
- 小さな単発作業は委譲せず、メインエージェントが直接処理してよい
- サブエージェントは別のサブエージェントを起動しない
- 各サブエージェントの報告は、結論、根拠、未確定事項、検証結果だけに絞る

#### researcher

- 実装前のコードベース調査、影響範囲確認、仕様確認、根拠収集に使用する
- 調査対象と確認事項が独立している場合のみ、複数の読み取り専用タスクを並列化できる
- ファイル変更を許可しない

#### implementer

- 成功条件、実装方針、対象ファイルが確定した後に使用する
- 同時に動かす書き込み担当は 1 体だけとする
- 対象ファイル、禁止事項、検証コマンドを委譲時に明示する
- 実装中に設計変更が必要になった場合は、独自判断で範囲を広げずメインへ戻す

#### reviewer

- 非自明な実装が完了した後に使用する
- 原則として差分と関連ファイルだけを確認する
- レビュー対象を編集させない
- 指摘がある場合は、メインが採否を判断してから implementer に修正を戻す

#### 並列実行

- 複数エージェントに同じファイルを並行編集させない
- 並列化は、独立した読み取り、調査、ログ解析に限定する
- researcher、implementer、reviewer の工程は原則として直列に実行する

#### フォールバック

- モデル未提供、起動失敗、権限不足が発生した場合、同じ委譲を反復しない
- 失敗理由、完了済み作業、未完了事項をメインへ戻す
- Haiku が利用できない場合は Sonnet、Sonnet も利用できない場合は親モデル継承を使用する

#### 高リスク作業

認証、権限、課金、個人情報、データ移行、破壊的操作、本番基盤の変更は、メインエージェントが直接判断する。
通常の reviewer だけでは不十分な実績が確認された場合に限り、Opus を使用する追加レビューを検討する。

### 3. 完了前に必ず検証する

- 動作を証明できるまで、タスクを完了とマークしない
- 必要に応じてmainブランチと自分の変更の差分を確認する
- 「スタッフエンジニアはこれを承認するか？」と自問する
- テストを実行し、ログを確認し、正しく動作することを示す

### 4. エレガントさを追求する（バランスよく）

- 重要な変更をする前に「もっとエレガントな方法はないか？」と一度立ち止まる
- ハック的な修正に感じたら「今知っていることをすべて踏まえて、エレガントな解決策を実装する」
- シンプルで明白な修正にはこのプロセスをスキップする（過剰設計しない）
- 提示する前に自分の作業に自問自答する

### 5. 自律的なバグ修正

- バグレポートを受けたら、手取り足取り教えてもらわずにそのまま修正する
- ログ・エラー・失敗しているテストを見て、自分で解決する
- ユーザーのコンテキスト切り替えをゼロにする
- 言われなくても、失敗しているCIテストを修正しに行く

### 6. Worktree ベースの開発フロー

- コード変更を伴う作業は、原則として専用ブランチと専用 worktree で開始する
- 例外: 既存PRへの追記修正、数分で終わる軽微な修正、緊急対応で即時修正が必要な場合
- メインの作業ディレクトリ（worktree 外）で作業を開始しようとした場合は、worktree の作成を提案する
- worktree 内かどうかは `git rev-parse --git-dir` の結果で判定する
  - `.git` または `/worktrees/` を含まないパス → メインの作業ディレクトリ
  - `/worktrees/` を含むパス → worktree 内
- **worktree はプロジェクト内の `.worktrees/` ディレクトリに作成する**
  - プロジェクトディレクトリ配下に作成することで、ディレクトリアクセスの許可プロンプトを回避できる
  - 作成コマンド: `git worktree add .worktrees/<branch-name> -b <branch-name>`
  - `.worktrees/` は `.gitignore` に追加済みであること（未追加の場合は追加する）

### 7. 長時間タスクの進捗報告

- 多数の項目を処理するタスクは、チャンク単位（例: 10 件ごと）に commit & push し、進捗を報告する
- 処理が継続しているか・止まっているかをユーザーに質問させない。節目ごとに「N/M 件完了」を自発的に伝える
- 中断・再開できる設計にする（処理済みリストや manifest を残す）

### 8. スコープ復唱（変更着手前）

- 変更に着手する前に、対象のファイルパス・ページパスを明示して認識を合わせる
- 類似ターゲットが複数存在する場合（例: 複数サービスの contact ページ、同名ファイル）は、推測で進めず着手前に対象を確認する
- 指示と実際の対象が食い違っていたら、作業を進める前に指摘する

## Git ワークフロー

- **ブランチ作成前**と **push 前**にデフォルトブランチを検出し、`git fetch --all` と rebase で最新化する
- 作業を始める前に、デフォルトブランチにいる場合、リモート(origin)と同期が取れているかを `git fetch origin` と `git status` で確認する。同期が取れていない場合（behind がある場合）、ユーザーに警告する

## git commit メッセージルール

- **形式**: Conventional Commitsに従う
  - `<type>(<scope>): <description>`
  - 例: `feat(auth): add login validation`
- type は `feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` / `build` / `ci` / `chore`
- **破壊的変更**: `!`を付与（例: `feat!: remove deprecated API`）
- **重要**: コミット単位でissue番号に紐づけない
  - issue番号はPull Requestに紐づける

## Pull Requestのルール

- リポジトリに `PULL_REQUEST_TEMPLATE.md` が存在する場合、その内容に従ってください
- タイトルは「git commit メッセージルール」と同じConventional Commits形式の英語、本文は日本語で記述してください
- 可能な限りissue番号を関連付けてください
  - 例: `- {issue番号}`
- 特に指定がない場合、draft モードで作成してください
- 作成後に GitHub Copilot をレビュワーに追加してください
- 1PRにつき1つの目的に集中してください
