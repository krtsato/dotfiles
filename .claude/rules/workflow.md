# 作業の進め方

## Plan モード

| 使う | 使わない |
| --- | --- |
| アーキテクチャの変更、高リスク、複数領域にまたがる非自明な作業 | 小さく明確な単発作業 |
| 構築だけでなく**検証の手順**にも | 計画を作ること自体が目的になる場合 |

途中でうまくいかなくなったら、無理に進めず立ち止まって計画し直す。
実装前に詳細な仕様を書いて曖昧さを減らす。結果を示すときは**計画ファイルのパスも出す**。

### 計画ファイルの書式

**見出しの直後に要約、その後に `<details>` で詳細。最初からこの形で書く**（後から要約を足さない）。

| 項目 | 決まり |
| --- | --- |
| 要約の長さ | **150 字以上**（空白を除く）。詳細を開かずに中身が分かる水準 |
| 視覚要素 | **表**を使う。並列でない列挙のときだけ箇条書きにする。文章だけにしない |
| 専門語 | 英単語をそのまま置かず**日本語に言い換える**（全大文字の略語とコード表記は可） |
| 見出し | **`（）` を使わない**。修飾は ` — ` で繋ぎ、日付や但し書きは要約へ移す |

`~/.claude/hooks/plan-format.sh` が `plans/*.md`・`plan-*.md`・`docs/plan*.md` を書いた直後に検査する。

## 対象機能が多いときは課題に割る

1 つの変更要求に収まらない規模なら、**親の課題 1 本と子の課題**に割る。子 1 本につき機能 1 つ。

| 手順 | 中身 |
| --- | --- |
| 1 | 計画を書く |
| 2 | **`codex exec -s read-only` でレビューを受ける**（出力は `tail` で受ける。`head` だと途中で切れる） |
| 3 | 指摘を反映し、**校正後の全文**を課題の本文に貼る |
| 4 | 着手したら **draft の変更要求**を作り、Copilot をレビュワーに割り当てる |
| 5 | 指摘を 1 件ずつ仕分けして解決済みにする |
| 6 | **進捗は課題にコメントする** |

計画は曖昧にせず詳細に書く。**リリース戦略**（入れた時点で何が起きるか・戻し方）まで書く。

## Worktree

コード変更は専用ブランチと専用 worktree で始める。例外は下の 3 つだけ。

```sh
git worktree add .worktrees/<branch-name> -b <branch-name>
```

| 例外 | |
| --- | --- |
| 既存 PR への追記 | worktree を作らなくてよい |
| 数分で終わる軽微な修正 | 同上 |
| 緊急で即時に直す場合 | 同上 |

- **`.worktrees/` はプロジェクト内に作る**（ディレクトリ許可の確認を避けるため）
- `.gitignore` に `.worktrees/` を入れておく
- いまいる場所は `git rev-parse --git-dir` で判定する。`/worktrees/` を含めば worktree の中

メインの作業ディレクトリで始めようとした場合は、worktree の作成を提案する。

## 長時間の作業

- 多数の項目を処理するときは、**10 件ごと**にコミットして進捗を伝える
- 「進んでいるか止まっているか」をユーザーに質問させない。節目ごとに「N/M 件完了」を自発的に伝える
- 中断と再開ができる形にする（処理済みの一覧や manifest を残す）

## 着手前のスコープ確認

- 対象のファイルパスやページパスを**明示して**認識を合わせる
- 似た対象が複数あるときは、推測で進めず着手前に確認する
- 指示と実際の対象が食い違っていたら、進める前に指摘する
- **条件つきの指示は狭い方に読む。** かかり先が 2 通りなら、後から足せる方を採る
