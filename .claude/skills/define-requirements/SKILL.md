# 要件定義

意思決定者が合意する業務結果、対象外、受入条件を、根拠と追跡可能な形で整理する。要件、設計、UI、契約、内部検討を混ぜず、根拠のない動作や数値を加えない。

## 重要事項

- 編集前に、読者、目的、利用場面、合意範囲、編集正本、提出物を確認する。既存情報から決められない場合だけ、成果物の責任範囲を左右する点を確認する。
- 根拠資料は合意状態、版、決定権限を確認して扱う。矛盾は推測で解消せず、出典、矛盾内容、確認先、未決状態を台帳へ記録する。
- 根拠資料そのものは変更しない。要件は編集正本へ反映し、派生成果物は必要な範囲だけ更新する。
- 明示承認済みの変更は再承認待ちにせず、合意範囲内で反映する。承認範囲が不明なコメントは本文を変更しない。
- Markdown 更新だけを依頼された場合は、実装や外部文書の更新へ広げない。範囲外に不整合が残る場合は、影響と未反映箇所を報告する。

## ユースケース

| 依頼 | 行うこと | 成果 |
| --- | --- | --- |
| 根拠資料から要件を作る | 出典を追跡し、要件と設計を分類する | 合意範囲が明確な要件案 |
| 既存要件を変更する | 編集正本と影響範囲を確認する | 整合した変更成果物 |
| コメントに対応する | 承認範囲だけを限定更新する | コメントと書式を保護した反映 |

## 成功基準

- 根拠資料の要求または内部参照の 100% が、要件、対象外、確認事項のいずれかへ対応付く。
- 意思決定者が必要な業務結果と受入条件を判断でき、実装詳細や未合意事項を誤って合意対象にしない。

## 前提条件

本文の起案に必須のランタイムはない。根拠資料と編集正本へアクセスできること。検証例には Git、`rg`、Node.js と npm が必要で、Markdown の検査は案件指定の linter を優先する。外部文書の更新には対象サービスの権限、限定更新、コメント・書式の読み戻し手段が必要である。

## 進め方

依頼に必要な手順だけを適用する。前提と根拠が明確な軽微な変更では、再調査せず変更と検証へ進む。

1. [文書チャーター](references/boundaries.md)で、読者、合意範囲、根拠資料、編集正本を定める。
2. 根拠資料を分類し、要求または決定事項を全件追跡する。識別子がない資料は、ページ、節、議事日時などの内部参照を付け、存在しない要求識別子を作らない。既存識別子を改番・再利用しない。提出文書では内部識別子を説明し、未作成ファイルへの参照に依存させない。
3. 業務要件、受入条件、設計、UI、契約、内部検討を分類する。新規作成・大規模再構成、または変更の影響が及ぶときは、非機能、権限、運用、アクセシビリティの該当性を確認し、未確認事項を確定扱いにしない。
4. 各要件は主体、条件または操作、必要な結果、対象外を明確にし、同じ決定の編集正本を 1 つにする。画面例と参考実装は理解補助であり、合意根拠にはしない。
5. 数値、性能、AI 精度などを条件にする場合は、[数値条件](references/boundaries.md#数値条件)を満たす。業務効果または利用者の作業負荷との関係を示し、未知の閾値を発明しない。
6. 受入条件は、合意した要件を現実的に確認できる前提、操作、期待結果にする。実装形式、再現困難な障害、未合意の完全性や精度を約束にしない。「すべて」「必ず」「完全」は範囲と実施可能性を確認する。
7. 変更時は、[横断整合性](references/review-and-consistency.md)に従い影響対象を先に列挙し、文字列検索と意味上の依存確認を行う。旧表記の検索対象から履歴と変更禁止の原資料を除外する。
8. コメント付き外部文書を更新する場合は、利用可能な CLI または接続ツールの実際の操作名、更新範囲、検証方法を先に確定する。編集正本を先に更新し、対象箇所だけを限定更新する。更新前後でコメント、リンク、書式を比較できない場合は完了扱いにしない。
9. 依存関係と未決事項に応じてレビュー単位を分ける。すべてを同じ段階数に固定しない。

## 完了チェック

- [ ] 根拠、合意状態、矛盾、未決事項が追跡できる
- [ ] 要件、設計、UI、契約、内部検討が分離されている
- [ ] 要求にない動作、数値、技術方式を追加していない
- [ ] 新規作成・大規模再構成や影響のある変更では、非機能、権限、運用、アクセシビリティの該当性を確認した
- [ ] 数値条件の範囲、材料、ばらつき、併用指標、根拠を記録した
- [ ] 受入条件が確認可能で、過剰な約束になっていない
- [ ] 変更対象の表、データ、画像、リンク、実装を必要な範囲で確認した
- [ ] 利用可能な Markdown linter、差分確認、関連する検証の結果を記録し、実行できない検証は理由を示した
- [ ] 外部文書を更新した場合、コメント、リンク、書式を読み戻した

## レビュー

まず根拠からの漏れと成果物間の整合を確認する。受入・契約のリスクがある場合は過剰な約束、提出文書では読者に不要な内部情報も検査する。大きな調査・レビューを委譲できる環境では、調査担当とレビュー担当へ対象と観点を分けて渡し、期待する結論を与えない。担当からさらに委譲しない。確認が必要な場合は利用環境の質問ツールを使用する。
