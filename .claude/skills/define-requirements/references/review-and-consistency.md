# レビューと整合性

## レビュー順

要件数が多い場合は、依存関係と未決事項に基づいて、無理なくレビューできる単位に分ける。

1. 用語、対象範囲、入力、識別情報
2. 主要な業務処理と正常系
3. 例外、複雑な操作、保存、受入、契約条件

文書番号とレビュー順を分離する。レビュー順を変えても文書識別子を変更しない。

各段階は、対象要件へのコメントが反映済みまたは明示的に保留され、後段へ引き継ぐ前提が分かる状態で完了とする。後段の変更が確定済み要件へ影響する場合は、影響箇所だけを再レビューする。

## 編集正本の決定

各要件について、編集正本となる文書を 1 つ決める。受領した提案書、要求書、CSV などの根拠資料は変更せず、編集正本の判断根拠として扱う。

```text
根拠資料 → 編集正本となる要件定義書 → 画面例・CSV・設計書・外部文書
```

関連文書では同じ要件の決定内容を重複管理しない。読者や文書の責務に必要な要約、参照、差分は記載してよい。

## 横断変更チェック

変更前に、影響対象を表にする。

| 対象 | 確認内容 |
| --- | --- |
| 要件定義書 | 編集正本、対応表、追加要件、用語、依存関係、受入条件 |
| データ | CSV、JSON、スキーマ、サンプル、ログ項目 |
| UI | モックアップ実装、画面画像、画像内文字、画面番号 |
| 文書 | README、設計書、運用書、提出物一覧 |
| 参照 | ファイルリンク、セクションリンク、画像リンク、生成設定 |
| テスト | スナップショット、受入条件、生成・検証スクリプト |

文字列検索は必要だが十分ではない。例えば識別子の例 `operation_id` を変更した場合、フォルダ名、親概念、説明文との意味上の一貫性も確認する。

## 表の整合性

- 入力列には利用者が入力する値だけを書く。
- 初期値列には画面表示時に設定される値だけを書く。
- 保存列には永続化する内容と確定時点だけを書く。
- 出力列には生成するファイルやデータだけを書く。
- 画面を開く、遷移する、複製を開始する動作を保存と書くのは、合意した自動保存が実行される場合だけにする。
- 要件一覧で十分な内容を、結果表や処理表で繰り返さない。

## コメント付き文書の更新

コメント付きのレビュー中文書では、本文だけでなくコメント位置と書式を保護する。

### 更新前

1. 文書 ID と対象セクションを確定する。
2. コメント ID、本文、解決状態、アンカー、引用文、返信を取得する。
3. 対象箇所の文字範囲、表、リンク、書式を読み取る。
4. 更新前リビジョンまたは復元可能なスナップショットを記録する。
5. 合意済み、またはユーザーが明示承認した変更だけを対象にする。

### 更新

1. 文書チャーターで定めた編集正本を先に変更する。
2. 対象段落、表セル、表行だけを限定更新する。
3. セクション全体や本文全体を置換しない。
4. 大きな更新は、文章、表、リンクを分けて反映する。
5. リビジョン制御が使える場合は、更新前リビジョンを指定する。
6. 部分的に失敗した場合は追加更新を止め、成功箇所と未反映箇所を記録する。

### 更新後

1. 新しい本文を読み戻す。
2. リンク先、文字色、下線、フォント、背景色を確認する。
3. 更新前後でコメント状態を比較する。
4. コメント件数だけでなく、アンカーと引用文が一致することを確認する。
5. 編集正本、外部文書、画面例、データ定義の整合性を確認する。

コメントのアンカー、引用文、返信、解決状態を保護できない場合は、更新を完了扱いにしない。自動でコメントを再作成または解決せず、影響と復旧方法を報告する。

部分更新に失敗した場合は、記録したリビジョンまたはスナップショットから安全に復元できるときだけ戻す。復元が他の編集者の変更を失わせる可能性がある場合は、自動で戻さず状況を報告する。

## 独立レビュー

| レビュー | 主な観点 |
| --- | --- |
| Completeness Review | 根拠資料の要求漏れ、識別子または内部参照の対応漏れ、非機能・権限・運用・アクセシビリティの該当性 |
| Devil's Review | 過剰な約束、検収リスク、実施困難な条件 |
| Consistency Review | 名称、ID、表、CSV、画像、リンクの不整合 |
| Audience Review | 読者に不要な内部情報、説明不足な前提 |

独立性を保つため、レビュー担当へ期待する結論や疑わしい箇所を先に伝えすぎない。
