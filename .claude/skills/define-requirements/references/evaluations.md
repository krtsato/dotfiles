## トリガーテスト

### Should Trigger

- 「提案書と議事録から要件定義書を作成して」
- 「既存要件をレビューして、設計詳細を書きすぎている箇所を整理して」
- 「名称変更を要件定義書、CSV、画面例の画像、外部文書へ漏れなく反映して」
- 「受入条件が過剰な約束になっていないか確認して」
- 「提案書にない過剰な要件や画面例がないか点検して」
- 「社内プロダクトの要求と議事録が矛盾しているため、未決事項を整理して」

### Should NOT Trigger

- 「Flutter の状態管理を設計して」: 実装設計だけを扱う。
- 「この画面の色と余白を調整して」: UI スタイリングだけを扱う。
- 「この Pull Request をコードレビューして」: 通常のコードレビューを扱う。
- 「CSV を集計してグラフを作って」: 要件定義を伴わないデータ分析を扱う。

## シナリオ 1 新規要件定義

依頼:

```text
提案書とPoC資料をもとに、業務アプリの要件定義書を作成してください。
```

期待する動作:

- 文書の読者、目的、合意範囲を先に確認または発見する。
- 提案書を一次情報、PoC を参考資料として分類する。
- 要求識別子（無い資料は内部参照）を全件抽出し、台帳に対応表を作る。
- 要件と設計を分離する。
- 依存関係に基づく段階レビューを提案する。

入力と期待出力:

| 入力の根拠 | 要件に保持する内容 |
| --- | --- |
| 「招待送信の前に、宛先と付与権限を確認画面で確認する」 | 送信前の確認画面で宛先と付与権限を確認できる |
| 「担当拠点へ招待できる」 | 担当拠点へ招待できる。担当拠点だけに限定する制約は追加しない |

失敗条件:

- PoC の画面やログ形式を本番要件として無条件に採用する。
- 要求にない機能を追加する。

## シナリオ 2 追加要求の横断反映

依頼:

```text
表示名を変更し、要件定義書、CSV、画面例の画像、外部文書へ漏れなく反映してください。
```

期待する動作:

- 編集前に影響対象を列挙する。
- 文字列一致だけでなく意味上の依存を確認する。
- 根拠資料の CSV は更新対象か確認する。
- 外部文書を限定更新し、コメントと書式を検証する。

失敗条件:

- Markdown だけを更新して完了とする。
- 外部文書のセクション全体を置換する。

## シナリオ 3 ログ要件の簡素化

依頼:

```text
ログ要件が詳細すぎるとレビューコメントを受けました。整理してください。
```

期待する動作:

- ログが誰の要求かを確認する。
- 意思決定者と合意する目的・保持・出力だけを要件へ残す。
- フィールド、内部形式、ファイル構造を設計書へ分離する。
- 重複セクションを統合または削除する。

失敗条件:

- 内部設計を少し言い換えただけで要件へ残す。
- 将来の保険という理由だけで詳細を契約対象にする。

## シナリオ 4 受入条件レビュー

依頼:

```text
受入条件が過剰な約束になっていないかレビューしてください。
```

期待する動作:

- 実施可能性、検収リスク、実装依存を確認する。
- 固定件数、完全性、AI 精度、再現困難な障害を重点確認する。
- 削除、抽象化、設計書への移動を提案する。

失敗条件:

- 詳細であるほど良いと判断する。
- 実行できない試験を残す。

## シナリオ 5 コメント付き外部文書の更新

依頼:

```text
外部文書のコメントに対応し、編集正本にも反映してください。
```

期待する動作:

- 合意済みコメントだけを対象にする。
- 更新前のコメント状態を保存する。
- 編集正本を先に更新し、外部文書を限定更新する。
- 更新後にコメントのアンカー、引用文、返信、解決状態、書式を比較する。

失敗条件:

- コメントへの回答が未合意のまま本文を変更する。
- 文書全体を再生成する。

## シナリオ 6 数値条件と自動保存

依頼:

```text
検出精度と自動保存を受入条件に含めるべきか整理してください。
```

期待する動作:

- 範囲、分母、評価資料、測定条件、ばらつき、併用指標、利用者の作業負荷を確認する。
- AI 精度を一律に除外せず、合意状態に応じて要件、開発中の評価、未決事項に分類する。
- 自動保存が合意されている場合だけ、画面遷移や開始操作を保存として扱う。

失敗条件:

- 根拠のない閾値を受入条件へ追加する。
- 自動保存の合意がないのに保存と断定する。

## 機能テスト観点

| 観点 | 確認内容 |
| --- | --- |
| Valid outputs | 要求、要件、対象外、確認事項が根拠資料と対応し、文書が抽象から具体の順に整理される |
| External operations | コメント付き外部文書を更新する場合、対象箇所だけが更新され、更新結果を読み戻せる |
| Error handling | 資料、権限、更新手段が不足する場合、推測や全置換を行わず影響を報告する |
| Edge cases | 要求識別子なし、根拠資料の矛盾、数値条件、自動保存、名称変更、コメント付き外部文書を適切に扱う |

## ベースライン比較

同じ根拠資料で、スキルなしとありの結果を比べる。スキルの価値は次の差に出る。

| 観点 | スキルなしで起きやすいこと | スキルありの期待 |
| --- | --- | --- |
| 範囲 | 便利そうな機能（並び替え、発信、期間の切り替え、税の表示）が要件や画面例に混ざる | 全項目を要求識別子または内部参照へ対応付け、対応しない項目は既定で削除する |
| 未決 | 不明点を推測で埋め、確定した要件として書く | 未決事項を確認事項として問い、要件にしない |
| 詳細 | 設計詳細や固定値が受入条件になる | 業務結果だけを受入条件にし、設計詳細は設計書へ移す |
| 変更 | 1 か所だけ直り、他の文書や画面例と矛盾する | 影響対象を先に列挙し、旧表記を検索して 0 件を確かめ、意味上の依存も確認する |
