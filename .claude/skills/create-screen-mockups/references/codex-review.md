# codex による画面レビュー

codex に画面例をレビューさせるときに読む。依頼文の例、実行コマンド、指摘の仕分け方を置く。

## 実行

依頼文はファイルにして標準入力で渡す。画像は実在する一覧画像を全部、`-i` にカンマ区切りで 1 回だけ渡す。

```sh
# Values: SHEETS is the contact-sheet output dir from step 6; PROMPT_FILE holds the prompt below.
SHEETS=/tmp/sheets PROJECT_ROOT=<project-root> PROMPT_FILE=/tmp/codex-prompt.md LOG=/tmp/codex.log
IMAGES=$(ls "$SHEETS"/sheet-*.png | paste -sd, -)
echo "passing $(echo "$IMAGES" | tr ',' '\n' | wc -l | tr -d ' ') sheet(s)"   # must equal the sheet count
codex exec --skip-git-repo-check -s read-only -C "$PROJECT_ROOT" \
  -i "$IMAGES" \
  - < "$PROMPT_FILE" > "$LOG" 2>&1
# The answer is everything after the last line that is exactly "codex".
awk '/^codex$/{buf=""; f=1; next} f{buf=buf $0 "\n"} END{printf "%s", buf}' "$LOG" | sed '/^tokens used$/,$d'
```

| 指定 | 理由 |
| --- | --- |
| `-i a,b,c` を 1 回 | `-i a -i b "依頼文"` と書くと、`-i` が後ろの依頼文まで画像パスとして読み、依頼文が空になる |
| `- < file` | 依頼文を標準入力から渡す。長い日本語の依頼文で引用符の扱いを誤らない |
| `--skip-git-repo-check` | Git 管理外のディレクトリでは、これがないと実行を拒否する |
| `-s read-only` | レビューでファイルを変えさせない |
| 出力をログに保存してから抽出 | 途中経過が数千行出る。終了コードが 0 でも中身が空のことがあるので、必ず本文を確認する |

数分かかるので、裏で実行して終わるのを待つ。一覧画像が 10 枚（40 画面）を超えるときは、1 回の入力に収まらず画面ごとの指摘が薄くなるため、アプリの利用者の種類などのまとまりごとに分けて実行し、指摘を 1 つの仕分け表にまとめる。

## 依頼文の例

```text
あなたはモバイル業務アプリの UI/UX と Flutter 実装に精通したシニアデザイナー兼エンジニアです。
添付は <製品の説明> の画面例 <N> 枚を 4 枚ずつ並べた一覧です（順番は <screens README> の画面一覧どおり）。

読むべきファイル:
- <project-root>/DESIGN.md（A2UI v0.9.1 基本カタログ＋Material 3。「AI っぽく見せないための規則」あり）
- <要件書>（画面にない情報を足さないこと）
- <確認事項>（未決の点の根拠）
- <screens README>（画面一覧と未決の点）
- <src/app.js, styles.css>（画面例の原本）

利用状況: <場所、姿勢、手袋、日差し、通信、頻出の作業>

観点:
1. ヒューマンインタラクション: 視覚的な階層と注意の誘導、情報の優先順位、片手操作、誤操作の防止、状態のわかりやすさ、一貫性、屋外での視認性、認知負荷
2. タイポグラフィ: 書体の選択、サイズ・太さ・色の階層、単調さ
3. 技術: Flutter と Material 3 での実装しやすさ、A2UI カタログとの整合、アクセシビリティ、原本の HTML/CSS の問題
4. 要件との整合: 要求資料（提案書）にない機能・操作・表示項目の追加（便利そうなボタンや絞り込みを含む）、要件の項目の欠落
「生成 AI が作ったっぽい」箇所も指摘してください。

出力: 日本語。重要度順に最大 25 件（それ以上は 1 件ずつ根拠を確かめる仕分けが追いつかないため）。各件に「重要度（高/中/低）・対象 PNG 名・問題・根拠・具体的な直し方」。最後に最も効く改善 3 つ。ファイルは変更しないこと。
```

## 指摘の仕分け

1 件ずつ、根拠を原本・要件書で確かめてから次のどれかに振る。結論が正しくても根拠が違うことがあるので、結論と根拠を分けて検算する。

| 振り先 | 条件 | 例 |
| --- | --- | --- |
| 画面を直す | 要件の欠落、表示の崩れ、状態の欠落、注意の誘導の誤り | 要件にある連絡先が出ていない。失敗時の画面がない |
| DESIGN.md の規則に書く | 静止画では表せないが実装で守るべきこと | タップ領域 48px、文字 200%、キーボード表示時の追従、チップの横スクロール |
| 未決の点に書く | 確認事項の回答がないと決められないこと | 部署単位の設定の置き場所 |
| 見送る | 画面例の目的外、または誤り。理由を残す | 画面例用の HTML に読み上げ属性がない（実装は Flutter の標準部品が担う） |

「静止画なのでスクロールできない」は、画面例では原則として見送る。ただし「その結果、要件の項目が 1 枚にも写っていない」なら、見出しを詰めるか、スクロール後の画面を足して直す。

## 仕分け結果の伝え方

依頼者には、件数の内訳（直す・規則に書く・未決の点に書く・見送る）と、見送った理由を表で示す。
