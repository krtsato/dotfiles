# 範囲の点検

画面の要素が要求資料（提案書）と要件書の範囲に収まっているかを点検するときに読む。手順のステップ7で必ず行い、依頼者から「過剰な要件や UI はないか」と聞かれたときも同じ手順で行う。

## 原則

要求資料にない機能・操作・表示項目・数値は、便利そうでも画面に置かない。画面例に置いたものは、依頼者やその先の発注者に「合意済みの機能」と受け取られ、見積や受入の範囲を黙って広げる。

## 手順

1. 画面ごとに、意味を持つ要素を全部書き出す。表示する項目、ボタンとアイコンボタン、メニュー、チップ・絞り込み・並び替え、タブ、切り替え、ダイアログ、説明の文、時刻・件数・容量などの数値。
2. 要素を 1 つずつ次に振る。

   | 分類 | 条件 | 扱い |
   | --- | --- | --- |
   | 対応あり | 要求資料の番号（無ければ節）に対応する | 残す。README の画面一覧の要件番号で追える |
   | 共通の操作 | 戻る・閉じる・ナビゲーションバー・ステータスバーなど、どのアプリにもありアプリの機能を足さないもの | 残す。新しい能力（発信、地図、並び替え、期間の選択、更新、撮影の設定など）を含むものは共通の操作に入れない |
   | 仮 | 要求資料の機能を描くのに必要だが、形が未決 | 残し、README の未決の点に確認事項の番号付きで書く |
   | 過剰 | 上のどれにも当たらない | 消す。ただし依頼者の判断が要るもの（例: 税の扱い、集計の期間）は、消したうえで確認事項に問いとして足し、README の未決の点にも確認事項の番号付きで書く |

3. 過剰な要素を消し、消したことで食い違う架空データを整える（例: 税の表示を消したら、明細の合計と金額を一致させる）。
4. 書き出し直し、点検表で描画と範囲を確認する。README との照合はステップ10で行う。
5. 依頼者には、過剰として消した要素を「画面・要素・要求資料との関係」の表で報告する。

## 付け足されやすい要素

画面を「それらしく」するために足されがちで、要求資料に無いことが多い要素。見つけたら要求資料を検索して根拠を確かめる。

| 要素 | よく出る場所 | 根拠になる要求の例 |
| --- | --- | --- |
| 電話の発信ボタン、地図を開くボタン | 連絡先・住所の行 | 「電話をかけられる」「地図で開ける」 |
| 並び替え・絞り込みの操作 | 要求が 1 つの一覧にしか書いていないのに、ほかの一覧にも付ける | 一覧ごとの「並び替えできる」「絞り込める」 |
| 期間の切り替え、更新ボタン、「◯時点」の表示 | 集計・ダッシュボード | 集計の期間、更新の方法・頻度 |
| 検索ボタン | 件数の少ない一覧（例: 担当者、場所） | 一覧ごとの「検索できる」 |
| フラッシュ・ズームなど撮影の設定 | カメラ | 撮影時の設定 |
| 容量・撮影日時などの付帯情報 | 写真の一覧・登録 | 表示する項目の列挙 |
| 税の表示、合計・小計の行 | 見積・金額 | 税の扱い、合計の表示 |
| 一覧から選んで自動で入る入力 | 登録フォーム | マスタの参照、自動入力 |
| 処理の動きの約束（閉じても送信が続く、自動で保存される） | 処理中・登録 | 中断・再開の仕様 |

## 点検を任せるとき

画面数が多いときは、ファイルを変更しない調査担当に任せてよい。そのときは、こちらで挙げた候補を渡さない（先入観で点検が狭まる）。返ってきた結果は、上の表の語（並び替え、税、時点、発信、地図、期間 など）で要求資料を検索して検算する。検索で根拠が無いのに過剰に入っていない要素があれば、点検が漏れている。
