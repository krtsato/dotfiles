# 評価シナリオ

## Should trigger

| # | 入力例 | 期待動作 |
| --- | --- | --- |
| 1 | 「この調査結果を役員向けGoogle Slidesにして」 | 意思決定、証拠、物語を整理し、編集可能なデッキと全ページ検証結果を作る |
| 2 | 「既存スライドは唐突に話が飛ぶ。アジェンダと見出しを追加して」 | 既存テーマを維持し、章の問い、中扉、遷移を追加して並びを再設計する |
| 3 | 「説明が抽象的なので主語、術語、5W1Hを足して」 | 抽象表現を対象、数値、担当、期限、判定条件へ変換する |
| 4 | 「事業計画を投資委員会向け`.pptx`へ変換して」 | 事実と仮定を分離し、選択肢、損益、リスク、ゲートを比較できる資料を作る |

## Should NOT trigger

| # | 入力例 | 期待動作 |
| --- | --- | --- |
| 1 | 「SNS投稿用の一枚絵を作って」 | 起動しない。画像生成またはデザイン作成の機能を使う |
| 2 | 「このPDFを三行で要約して」 | 起動しない。スライド成果物を求めていない |
| 3 | 「既存デッキの誤字一文字だけ直して」 | 起動しない。物語・根拠・全体構成が対象外の軽微編集 |
| 4 | 「市場規模だけ調査して」 | 起動しない。調査結果をスライドへ変換する依頼ではない |

## Functional tests

| カテゴリ | シナリオ | 合格条件 |
| --- | --- | --- |
| Valid outputs | 十ページの新規Google Slidesを作る | 全ページが編集可能で、表紙、アジェンダ、結論、次の行動を含む |
| Authoring succeeds | 既存デッキへ中扉二枚を追加する | テーマとページサイズを維持し、順序とページ番号が同期する |
| Error handling | PDF exportが失敗する | 完了扱いにせず、原因を調べ、代替の正式なexport手段を試し、未解決なら明示する |
| Edge case | 情報量が既定枚数に収まらない | 文字を過度に縮小せず、付録化または枚数変更の根拠を示す |
| Edge case | 成功事例の数値定義が異なる | 一本のグラフへ混ぜず、条件と留保を付けた事例表にする |

## 前方評価シナリオ

### シナリオ1 新規の意思決定資料

**入力**：市場調査、競合比較、損益試算から、経営会議で参入可否を決める資料を作る。

**期待出力**：調査理由、方法、結果、示唆、選択肢、推奨案、実行ゲートが順番に並び、
主要数値へ出典または仮定ラベルが付いている。

### シナリオ2 既存資料の再構成

**入力**：二十五ページの既存資料は個別ページが整っているが、章の切り替えが唐突で、
抽象語が多い。

**期待出力**：アジェンダ、調査理由、中扉、5W1Hの具体ページを追加し、既存の事実と
デザインを保ったまま並び替える。全ページ再出力で回帰がない。

### シナリオ3 不完全な根拠

**入力**：売上だけを開示した成功談と、定義のない成長率が含まれる。

**期待出力**：利益や再現性へ読み替えず、運営主体、期間、指標、費用控除、未確認事項を
明示する。証拠が不足する判断は保留ゲートへ置く。

## 定期ブラッシュアップ評価

実際の利用で手戻りが発生した場合、次を記録してから最小の指示だけを改訂する。

- 依頼文と対象形式
- 初回成果物の問題
- ユーザーの訂正
- 根本原因が物語、証拠、実装、検証のどこにあったか
- 再発する普遍的パターンか、その案件だけの例外か

一案件だけの好みは普遍ルールへ昇格しない。同じ原因が複数回確認された場合に、最も
狭い有効範囲へ追加する。
