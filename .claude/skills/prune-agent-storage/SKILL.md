# 保存領域を片付ける

## Important

**この 3 つは絶対に消さない。** 検索経路から構造的に外してあるが、動きを変えるときも必ず守る。

| 場所 | 理由 |
| --- | --- |
| `memory/` | **セッションをまたいで残すことが目的**。古さは不要を意味しない |
| `plugins/` | 導入したコード本体。更新日時が古くても使われている |
| セッションログ | 約 30 日で自動的に入れ替わる。二重に消す必要がない |

**削除は履歴から戻せない。** これらの木は git リポジトリ内にあるが `.claude/.gitignore` が除外している。だから既定は一覧のみで、`--apply` はゴミ箱へ移すだけ。`--purge` を使うのは利用者が明示的に求めたときに限る。

## ユースケース

### Use Case 1: 保存領域が重くなったときの棚卸し

- **Trigger**: 「`~/.claude` が重い」「容量を空けたい」と言われた、または `du` で数百 MB を確認した
- **Steps**:
  1. 引数なしで実行し、種類ごとの件数と容量を確認する
  2. `tool-results` に資料が含まれていないか一覧で確かめる
  3. `--apply` でゴミ箱へ移す
- **Result**: 解放した容量と残り件数が出力され、ゴミ箱から復元できる状態で片付く

### Use Case 2: 古い計画だけの整理

- **Trigger**: 「古い plan を消して」「plans を整理して」と言われた
- **Steps**:
  1. `--only plans` で一覧を出す。各計画の見出しが表示される
  2. 進行中の案件が混ざっていないか見出しで判断する
  3. `--only plans --apply` で移す
- **Result**: 半年以上触っていない計画だけが片付き、最近直したものは残る

### Use Case 3: 溜まっているかどうかの確認だけ

- **Trigger**: 「session が溜まってないか」と聞かれた
- **Steps**:
  1. 引数なしで実行する
  2. 出力の「該当」行と種類ごとの内訳を読む
- **Result**: 0 件なら「溜まっていない」と答えられる。セッションログが自動で入れ替わる事実も添えて説明できる

## 対象と既定のしきい値

**しきい値が 2 段階に分かれているのが要点。**

| 種類 | 場所 | 既定 | 中身 |
| --- | --- | --- | --- |
| `plans` | `plans/*.md` | **180 日** | 書いた実装計画。しばらくは読み返す価値がある |
| `subagents` | セッション配下 | 30 日 | subagent ごとの記録 (`.jsonl`)。後から参照しない |
| `tool-results` | セッション配下 | 30 日 | ツールが取得した `.json` / `.pdf` / 画像 |
| `file-history` | `file-history/` | 30 日 | 編集前のファイルの退避 |

**計画だけ長いのは、読み返す対象だから。** 残り 3 種は過去の作業の副産物で参照されない。

## 使い方

```bash
~/.claude/skills/prune-agent-storage/scripts/prune-agent-storage.sh --only plans --apply
```

| 指定 | 動作 |
| --- | --- |
| なし | **一覧だけ出す。何も消さない** |
| `--apply` | ゴミ箱へ移す。`~/.Trash/agent-prune-<日時>/` に**元の階層を保って**入る |
| `--purge` | 完全に削除する。**取り消せない** |
| `--days N` | **全種類を N 日に揃える**。2 段階の既定を上書きする |
| `--only KIND` | 1 種類だけに絞る。`plans` / `subagents` / `tool-results` / `file-history` |

迷ったら `--apply` を選ぶ。ゴミ箱に入れておけば戻せるため、`--purge` は既定の選択肢にしない。

## 手順

**1. 一覧を出す。** 引数なしで実行する。種類ごとの件数・容量・適用した日数と、古い順の上位 10 件が出る。計画については見出しも表示され、何の計画だったか分かる。

**2. 取得物を確認する。** `tool-results` には調査の元資料が残っている場合がある。**消す前に中身を見る。** 必要なものがあれば別の場所へ退避してから進む。

**3. 消す範囲を確かめる。** 一覧に判断の難しいものが含まれていたら、`AskUserQuestion` で「全部」「1 種類だけ」「やらない」を利用者に選ばせる。**勝手に `--purge` を選ばない。**

**4. ゴミ箱へ移す。** `--apply` を付けて実行する。階層が保たれるので、戻すときに元の位置が分かる。

**5. 結果を照合する。** 出力の件数と、ゴミ箱に入ったファイル数が一致することを確かめる。そのうえで引数なしで再実行し、該当が 0 件になったことを確認する。

## 実行例

入力:

```bash

```

期待される出力:

```text

対象の種類: plans

セッションログ・memory・plugins は対象外です。
```

## 完了基準

次の 4 つがすべて満たされたときに完了とする。

- **該当が 0 件**になる。引数なしの再実行で確認する
- ゴミ箱に入ったファイル数が、出力の「削除したファイル数」と**一致する**
- `memory` / `plugins` / セッションログの件数が**実行前と変わらない**
- 利用者へ「削除した件数」と「残っている件数」を報告済み

## 実行チェックリスト

- [ ] 引数なしで一覧を出した
- [ ] `tool-results` に資料が含まれていないか確認した
- [ ] 判断が難しい場合は `AskUserQuestion` で範囲を確認した
- [ ] `--apply` で実行した (`--purge` は明示的な要求がない限り使わない)
- [ ] 移動先のパスを記録した

- [ ] `memory` / `plugins` / セッションログの件数が変わっていないことを確認した
- [ ] 削除件数と残り件数を報告した

## 落とし穴

**更新日時は書き換えで変わる。** 半年前に作った計画を先週直せば対象にならない。逆に作ったまま放置したものは確実に引っかかる。判断に迷うものは `touch` で日時を新しくすれば外れる。

**消すと惜しいのは取得物だけ。** 残り 3 種は副産物なので機械的に消してよい。`tool-results` は資料そのもので、日数だけで判断すると惜しいものが混ざる。`--only` で分けて扱う。

**編集前の退避を消すと巻き戻せなくなる。** 長く続くセッションでは、古い退避を消すとそこまでさかのぼる操作ができなくなる。実際にそこまで戻すことはまずないが、判断材料として覚えておく。

**空になったディレクトリは消える。** 移動後、中身が無くなった階層は片付ける。ただし根は残す。

**しきい値の境界は「より古い」。** `--days 30` はちょうど 30 日のものを含まない。

## Troubleshooting

エラーが出たら黙って飛ばさず、原因を突き止めてから進む。**件数を減らしたり対象を狭めたりして「通ったことにする」のは禁止。**

### Error: "claude directory not found: ..."

**Cause**: `CLAUDE_DIR` が誤っている、または `~/.claude` へのシンボリックリンクが切れている。

**Solution**:

1. リンクの指す先を `stat -f '%Y' ~/.claude` で確認する
2. 指す先が存在しない場合は dotfiles の配置をやり直す
3. 検証中であれば `CLAUDE_DIR` に渡したパスの綴りを確認する

### Error: "--days must be a non-negative integer, got: ..."

**Cause**: `--days` に数字以外を渡した。負数もここで弾かれる。

**Solution**: 0 以上の整数を渡す。しきい値を種類ごとに分けたい場合は `--days` を使わず `--only` で 1 種類ずつ実行する。

### Error: "--only must be one of: plans subagents tool-results file-history"

**Cause**: 種類名の綴り違い。`plan`、`tool-result` のような単数形は通らない。

**Solution**: 表記は表のとおり。複数種類を同時に絞ることはできないので、必要なら分けて実行する。

### Symptom: 一覧は出るのに 1 件も移動しない

**Cause**: 一覧の出力をパイプで受けている。`set -eo pipefail` の下では、受け手が先に終了するとパイプが壊れ、移動処理に到達する前にスクリプトが終わる。

**Solution**: 出力をファイルへリダイレクトしてから読む。過去にこの原因で 605 件が 1 件も移動しなかった実例がある。詳細は `references/evaluations.md` を参照。

## 動きを変えたときの確かめ方

`CLAUDE_DIR` と `TRASH_DIR` を差し替えると、本物に触らずに検証できる。検証シナリオと functional test の一覧は `references/evaluations.md` にある。**次の 2 点は必ず含める。**

**1. 件数を 20 件より多くする。** 一覧は上位 10 件だけ表示する。過去に出力をパイプへ渡していたとき、**10 件を超えると処理全体が止まり、1 件も移動しないという不具合を出した。** 3 件のテストでは境界に届かず、本番の 605 件で初めて露呈した。

**2. 守るべきものを仕込む。** 300 日前の `memory/MEMORY.md`、300 日前の `plugins/` 配下のファイル、300 日前のセッションログを置き、**いずれも残ることを確認する。**
