# 信用倍率が改善していて売買が活発な買い候補を出す

## CRITICAL: 先に読むこと

- **条件を緩めて件数を合わせない。** 要求件数に届かなければ、**届かない事実をそのまま報告**する。
  緩めると「条件に合った銘柄」ではなく「件数を満たした銘柄」になる。
- **「儲かる」と書かない。** このデータ基盤自身の検証結果は「単独の技法にエッジ無し」。
  出力は**「条件に合った」**であって推奨の保証ではない。**固定の注意を必ず添える**（[出力](#出力)）。
- **技法の重なりを確からしさとして読ませない。** 大半の銘柄に同じ技法（多くは一目均衡表）が入る。
- **倍率の急低下は良い意味とは限らない。** 表の「倍率が下がった理由」の列を必ず併せて読む。

## 用語

同じものを別の語で呼ばない。本文・スクリプト・参照文書はすべてこの正式名を使う。

| 正式名 | 意味 |
| --- | --- |
| 倍率が改善 | 条件 1。信用倍率が**約 3 週間前**より下がっている。**公表は日次なので、約 7 日おきに 4 時点を取る**。点が 4 つなら間は 3 つなので、張る期間は 3 週間 |
| 窓の起点 | 比べる 4 時点のうち一番新しい日。最新の公表で 4 時点が揃わないとき、**揃う日まで最大 6 日戻す**。戻した事実は標準エラーに出る |
| 売買が活発 | 条件 2。出来高比と当日代金の条件を満たす |
| 技法が該当 | 条件 3。講義由来の技法が台帳で**完成して**発火している。予兆だけの記録は数えない |
| 予兆 | 技法の**手前で成立する条件**（クロスの手前など）だけが満たされ、技法としてはまだ完成していない。**別の節**に出し、買い候補として扱わない。予兆の節には**条件 1（倍率）を当てず、条件 2 だけ**を当てる |
| 需給の裏付け | 予兆の節の並び順。条件 1 と同じ窓で 強（3 週連続で低下）・中（3 週前より低い）・なし・不明 の 4 段。**推奨の度合いではない** |
| 市場データの取得 | `scanner.tradingview.com` への問い合わせ。**1 回だけ** |
| 出来高比 | 直近の出来高が平均の何倍か |
| 順位の推移 | 売買代金の日次順位の変化 |
| 母集団 | 3 条件を当てる対象。既定は全市場、ウォッチリスト名を渡すとその日本株だけ |
| 外れた銘柄 | ウォッチリストの構成銘柄のうち条件に該当しなかったもの。**順位ではない** |

## ユースケース

### 1. 定例の絞り込み依頼

- **Trigger**: 「売買代金が日に日に上がっていて、信用倍率が改善傾向で、技法で買い推奨できる銘柄を 30 個」
- **Steps**: 市場データの取得（1 回）→ スクリプトで 3 条件を掛け合わせ → 要約・表・固定の注意を出す
- **Result**: 要約 1 行と表 4 つ（主表・⚠ 決算・買い候補ではない節・読みどころ）、固定の注意 3 文

### 2. 件数を変えた再実行

- **Trigger**: 「さっきの条件で 10 個だけ」「50 個出して」
- **Steps**: 件数を変えて再実行（`screen.sh 10` のように**位置引数**で渡す）
- **Result**: 同じ条件・同じ順序の上位 N 件

### 3. ウォッチリストの中だけで見る

- **Trigger**: 「ALL_半導体関連 の中で条件に合う銘柄は？」「商社で信用倍率が改善しているのは？」
- **Steps**: ウォッチリスト名を**第 2 位置引数**で渡す（`screen.sh 30 ALL_半導体関連`）
- **Result**: 該当した銘柄の表と、**該当しなかった構成銘柄を理由つきで**並べた節。
  名前が違えば近い候補が示されるので、そこから選び直す

### 4. もうすぐシグナルが出そうな銘柄を見る

- **Trigger**: 「もうすぐクロスしそうな銘柄」「シグナルが出そうな銘柄」「予兆のある銘柄」
- **Steps**: 通常どおり実行し、表の後ろの**予兆の節**を読む
- **Result**: 売買が活発で（条件 2 だけを当てる）、技法が手前まで来ている銘柄の表。需給の裏付けの順に並ぶ。**まだ起きていない**ことを必ず添える

### 5. 該当が少ないことの確認

- **Trigger**: 「今週は候補が少ない気がする」
- **Steps**: 通常どおり実行し、**絞り込みの各段階の件数**を読む
- **Result**: どの条件で落ちたかが分かる（例: 倍率改善 251 → 3 条件 32）

## 手順

### ステップ 1: 前提が揃っているか見る

```bash
ls ~/dev/me/mcp-tradingview/data/seido-margin-daily
```

`mtall*.jsonl` があり、**最新が数日以内**であること。無い・古いなら日次の取り込みが止まっている。
**その場合は絞り込みを続けず、取り込みの失敗を先に直す。**

**旧 `data/seido-margin/` を見ない。** そこは 2026-09-18 で終わった週次の保管庫で、
**常に存在する**ため、確認先にすると日次が死んでいても通ってしまう。

### ステップ 2: 絞り込みを実行する

引数は件数だけ。市場データの取得も 3 条件の判定も、**コンテナの中で**行う。
image は毎回作り直される（変更が無ければ 10 秒ほど。**tag の有無だけで済ませると古いコードで判定してしまう**）。

```bash
sh ~/.claude/skills/screen-margin-improving-stocks/scripts/screen.sh 30
```

ウォッチリストの中だけで見るときは、名前を**第 2 位置引数**で渡す。

```bash
sh ~/.claude/skills/screen-margin-improving-stocks/scripts/screen.sh 30 ALL_半導体関連
```

**コンテナを使うのは、実行するマシンによって結果が変わらないようにするため**（同じデータなら同じ表が出る）。

標準出力に表と**予兆の節**、標準エラーに**絞り込みの各段階の件数**（予兆のみの件数を含む）と
**技法の内訳**が出る。**両方を読む。**

**ウォッチリストで絞っても表の意味は変わらない**——載るのは条件に該当した銘柄だけで、
ウォッチリストを順位づけたものではない。該当しなかった構成銘柄は**別の節**に理由つきで出るので、
**その節を候補として読ませない**（[出力](#出力)）。

### ステップ 3: 要約と表を出す

[出力](#出力)の形をそのまま使う。**箇条書きの注意書きを足さない。固定の注意は省かない。**

### ステップ 4: 上位銘柄を掘り下げる（依頼があったときだけ）

「この銘柄をもっと詳しく」と言われた場合のみ、`Agent` ツールで調査を委譲する。
**メインの文脈を株価履歴や決算資料で埋めない。**

## 出力

**チャットは「要約 1 行・表 4 つ・固定の注意 3 文」で組む。注意書きを箇条書きで並べない。**
読み手は表を目で追う。長い箇条書きは読まれず、大事な ⚠ が埋もれる（2026-11-10 に利用者から指摘）。

| 決まり | 中身 |
| --- | --- |
| 説明は表の中 | 1 項目 1 行。2 行を超える説明は書かない |
| 数字は今回のもの | 毎回同じ説明は「固定の注意」の 3 文に寄せ、表には**その回の数字と銘柄名だけ**を書く |
| 当てはまらない行は消す | 「読みどころ」の表は、今回当てはまる行だけを残す |
| 全部入りの表はファイル | 標準出力をスクラッチパッドに保存し、**絶対パスを 1 行で示す**（終値・出来高比・上場株数比・枚数・技法の全名はそちら） |

### 1. 要約 — 1 行

`3 条件に合った 128 件のうち 30 件を表示。⚠ 決算が近い 11 件。倍率は 10-16 → 11-06 の 4 時点で比較（起点の戻しなし）`

起点を戻したときは**戻した日数**をここに書く（窓が数日古い表と最新の表は見た目が同じになる）。

### 2. 主表

| 列 | 書き方 |
| --- | --- |
| # ・コード・銘柄名・セクター | 標準出力のまま。銘柄名が長ければ「ホールディングス」を略してよい |
| 代金(億) | 当日代金 |
| 順位 | `223→93 (+130)`。不明は「—」 |
| 倍率 | `42.26→16.77` |
| 下がった理由 | 増減の**符号で一言**：買い減・売り増＝「両方」、買い減で売りが減または 0＝「買い残減」、売り増で買いが増または 0＝「売り残増」、読めない＝「不明」 |
| 次回決算 | ⚠ と日付と残り日数。今年の日付は月日だけでよい |
| 技法 | 本数（`8 本`）。名前はファイルの表と、読みどころの「技法の重なり」行で示す |

### 3. ⚠ 決算が近い

| いつ | 銘柄 |
| --- | --- |
| **今日 11-10** | ＳＵＢＡＲＵ（7270）・資生堂（4911） |
| 11-12 | 明治ホールディングス（2269） |

対象は**主表と予兆の銘柄**。静かな時期の ⚠ は、買い候補ではない節の表に件数だけ書く。
**⚠（7 暦日以内）の銘柄を全部、コードつきで載せる**。今日・明日は太字にする。表の直下に次の 1 行を毎回添える。

> 決算の内容しだいで大きく動きます。祝日を挟むと、⚠ が無くても 5 営業日の保有中に決算が来ることがあります。

0 件なら表の代わりに
「日付が分かった銘柄に、7 日以内の決算はありません」と 1 行書く（日付が「—」の銘柄があれば、その銘柄名も添える）。
2026-11-10、利用者は住友金属鉱山を持ったまま決算を迎え、知らずに急落に巻き込まれた。

### 4. 買い候補ではない節

予兆と静かな時期を 1 つの表にまとめる。**0 件でも行を残す**。

| 節 | 件数 | 銘柄 | 読み方 |
| --- | --- | --- | --- |
| 予兆 | 1 | 日置電機（6866）・需給の裏付け 中・RSI 抵抗ライン抜け × MACD クロス手前 | まだ起きていない（過去は 4〜17% が結局クロスしない）。効くかはまだ分からない |
| 静かな時期 | 31（30 表示） | 西武ホールディングス・テルモほか。うち ⚠ 13 件 | 売買が静かで落ちた。買う根拠にも、活発になるのを待つ根拠にもならない |

予兆が 1〜3 件なら銘柄・需給の裏付け・技法を書く。4 件以上なら上位 3 件と「ほか N 件」。
決着した予兆の記録の読み出し結果があれば、「効くかはまだ分からない」をその結果（20 営業日後の成績と明記）に置き換える。
予兆の銘柄のコード・セクター・次回決算はファイルの表に残る（標準出力の予兆の表がそのまま入る）。

### 5. 今回の読みどころ

**当てはまる行だけ**を残す。

| 項目 | 今回 | 残す条件 |
| --- | --- | --- |
| 絞り込みの経過 | 倍率改善 221 → 株式 203 → 売買が活発 151 → 技法が該当 128 | 毎回（標準エラーの各段階の件数） |
| 技法の重なり | 30 件中 29 件にボリュームオシレーター、26 件に一目均衡表 | 毎回（標準エラーの内訳の上位 2〜3 個。例の数字を写さない） |
| 主表の枠 | 順位あり 15・不明 15。省いた件数 19・79 | 毎回（標準エラーの「主表：」と「主表で省いた件数」） |
| 代金が小さい | 中部飼料（約 1 億円） | 1 億円前後以下の銘柄があるとき |
| 比較に使わなかった公表 | 2026-09-30。市場全体で売り残だけ膨らんだ日（権利取りの売り）で、銘柄の需給は変わっていないため外した | 標準エラーに出たとき |
| ウォッチリストの外れ | 条件で落ちた 12・記録に無く判定できない 5。銘柄ごとの理由はファイルの表 | 絞ったとき。**2 つを混ぜない**。候補ではない |

### 6. 固定の注意 — 3 文

次の 3 文を毎回そのまま書く。

> 条件に合ったというだけで、儲かるという意味ではありません（この基盤の検証では単独の技法に優位性はありません）。
> 技法の本数は重なりで確からしさではなく、「—」は分からないという意味で、決算日は予定なので買う前に会社の IR で確かめてください。
> 主表の後半（順位「—」）は前半より下位という意味ではなく、予兆・静かな時期の銘柄は買い候補ではありません。

### 表の各列の意味 — 聞かれたときに答える

チャットには書かず、利用者に聞かれたら答える。

| 項目 | 意味 |
| --- | --- |
| 順位「—」 | 上位 300 の記録外か、推移を確認できない。取引が無いのではない。主表は順位ありを前半、不明を後半に**半分ずつの枠**（奇数の余りは順位あり・未使用の枠は他方へ）で出し、後半は下位という意味ではない |
| 静かな時期の順位「—」 | 順位を照合していないため。上位 300 の外とは限らない |
| 倍率が下がった理由「不明」 | 残高を読めていない。変化が無かったのではない |
| 需給の裏付け | 信用倍率の動きで並べた順。強でも「条件に合った」にすぎない。「不明」は悪い値ではない |
| 予兆の講義上の扱い | 講義は予兆で動くことを支持する話と戒める話の両方をしている |
| 予兆の成績 | 予兆の記録は 20 営業日後に決着する。読み出し結果を載せるときは「20 営業日後の成績」と書く |
| 上場株数比・枚数 | 表示だけ。講義は需給を 1 日の出来高との比で測り〔66dceb86〕、上場株数・浮動株は字幕 265 本（2026-09-29 時点）に出てこない。「—」は記録が無い |
| 次回決算 ⚠ | 7 暦日以内。5 営業日の保有の目安で、祝日を挟むと ⚠ が無くても保有中に決算が来ることがある。「—」は分からない。条件にも並び順にも使っていない |

### 入出力の例

**入力**: 「信用倍率が改善していて売買が活発な買い候補を 5 個」

**出力**: 上の 1〜6 の順。2026-11-10 の実行なら要約は
`3 条件に合った 128 件のうち 5 件を表示。⚠ 決算が近い 1 件。倍率は 10-16 → 11-06 の 4 時点で比較（起点の戻しなし）`。

**入力**: 「該当が 3 件しかないなら条件を緩めて 30 件にして」

**出力**: 緩めない。「3 件しか該当しません」と報告し、**どの条件で落ちたか**（各段階の件数）を示す。

| 要約・表 4 つ（⚠ 決算は 0 件ならその 1 行）・固定の注意 3 文がある | [出力](#出力)と突き合わせる。⚠ の銘柄が全部載っている。読みどころに当てはまらない行が無い |
| 絞った場合、構成銘柄が全部どこか 1 か所に現れる | 技法が該当＋予兆のみの「売買が活発」の件数＋静かな時期の M 件（いずれも標準エラー）＋外れた銘柄（標準出力の見出し）＝母集団（標準エラー）。表は件数の上限で切れるので表の行数では数えない |

## Troubleshooting

### Error: `信用残高のファイルが見つかりません`

- **Cause**: `SCREEN_REPO` が mcp-tradingview を指していない、または日次データが未取得。
- **Solution**: `ls ~/dev/me/mcp-tradingview/data/seido-margin-daily` で `mtall*.jsonl` の存在を確認する。
  無ければ日次の取り込みが止まっている。**絞り込みを続けず、取り込みの失敗を先に直す。**

### Error: `基準日 … ごろの信用残高がありません`

- **Cause**: 4 時点ぶんの記録が揃っていない（新しい環境、または取り込みの停止）。公表が日次に
  なったので、**回数ではなく暦で 4 時点**（約 7 日おき・**目標日以前** 4 日以内。目標日より後の
  公表は使わない）を取る。どこか 1 つが埋まらないと比較しない。**間隔は基準日で測る**
  （公表日は切り替えで跳ぶため）。**起点を最大 6 日戻しても揃わなかった**ときにこれが出る。
- **Solution**: 取り込みの実行履歴を確認する。**時点を減らして回避しない**——
  時点を 3 つにすると比べる期間が 2 週間に縮み、傾向ではなく雑音を見ることになる。

### Error: `基準日 … ごろと同じ公表しかありません`

- **Cause**: 同じファイルが 2 つの時点に割り当たった＝その期間の公表が欠けている。
- **Solution**: **時点ごとの比較になっていないので、そのまま報告する。** 欠けた日は取り直せない。

### Error: `技法ノートが読めません`

- **Cause**: 技法ノートのパスが違う、または mcp-invest-knowledge が未クローン。
- **Solution**: `ls ~/dev/me/mcp-invest-knowledge/sources/technique-notes` を確認する。
  **技法名をローマ字の slug のまま出さない**——読み手が意味を取れない。

### 症状: 該当が 0 件になる

- **Cause**: 市場全体が閑散（売買が活発の条件で全滅）か、市場データの取得に失敗している。
- **Solution**: 標準エラーの**絞り込みの各段階の件数**を読む。「株式」の段階で 0 なら取得の問題、
  「売買が活発」の段階で 0 なら市場が閑散。**0 件は「該当なし」であって「エラー」ではない**ので、
  取得が正常なら 0 件をそのまま報告する。

### Error: `docker が見つかりません`

- **Cause**: Docker が未インストール、または起動していない。
- **Solution**: Docker を起動する。**やむを得ずホストで直接動かす場合は結果が Go の版に依存する**ので、
  そのことを報告に添える（コマンドはエラーメッセージが示す）。

### Error: `x509: certificate signed by unknown authority`

- **Cause**: image の土台に証明書が入っていない。`static-debian12:nonroot` ではなく
  `static-debian12:static-nonroot` を使うとこうなる。
- **Solution**: `Dockerfile.screen` の土台を確認する。**このコマンドは外部へ HTTPS で
  問い合わせるので、証明書の入った土台でなければ毎回失敗する。**

### 症状: コンテナとホストで結果が違う

- **Cause**: マウントしたパスが違う（別のリポジトリを指している）か、image が古い。
- **Solution**: `docker image rm tradingview-screen-margin:local` で作り直す。
  **結果が違うこと自体が異常**なので、報告する前に必ず原因を突き止める。

### 症状: 順位の推移が全部「—」になる

- **Cause**: 日次の順位記録が 8 営業日分に満たない、または該当銘柄が上位 300 の外。
- **Solution**: `ls ~/dev/me/mcp-tradingview/data/turnover-rank/japan` の件数を見る。
  8 日分未満なら記録の蓄積待ち。**「—」は「取引が無い」ではなく「上位 300 の記録外」**なので、
  そのまま報告してよい。

### Error: `ウォッチリスト "..." は正本にありません`

- **Cause**: 名前が違う。正本の名前は TradingView 上のウォッチリスト名と同一である。
- **Solution**: エラーが**近い候補を並べて出す**ので、そこから選び直す。
  候補が出ない場合は全件が並ぶ。**推測で別の名前を試さず、出た候補から選ぶ。**

### Error: `ウォッチリスト "..." に日本株がありません`

- **Cause**: 為替・指数・国債・米国株だけのリストを指定した。この絞り込みは
  **JPX の公表**を読むので、日本株以外には何も言えない。
- **Solution**: 日本株を含むリストを選ぶ。**全市場に黙って戻さない**——
  聞かれていない問いに答えることになる。

### Error: `分類の正本がありません`

- **Cause**: `mcp-invest-knowledge` に `sources/watchlists` が無い（未クローン、または未マージ）。
- **Solution**: `SCREEN_CANON` で場所を指定するか、絞らずに実行する。
  **絞らない実行は正本を読まない**ので、正本が無くても従来どおり動く。

### 症状: 外れた銘柄が全部「信用残高の記録に無い」

- **Cause**: そのウォッチリストが ETF・新規上場・整理銘柄中心で、JPX の公表に載っていない。
- **Solution**: **異常ではない。** 「条件に合わなかった」ではなく**「判定できなかった」**と報告する。
  この絞り込みは信用残高が前提なので、載らない銘柄には最初から何も言えない。

### 症状: 「起点を N 日戻した」と出る

- **Cause**: 最新の公表では 4 時点が揃わなかった。公表が週次から日次に変わった境目に
  **2026-09-19 から 09-24 の空白**があり、水曜・木曜の基準日を起点にすると 3 つの刻みすべてが
  2 日ぶん届かない。
- **Solution**: **異常ではない。条件は緩んでいない**——同じ 4 時点・同じ 3 差分で、
  窓の終わりが数日手前になるだけ。**戻した日数を出力に必ず書く。** 戻りは最大 6 日で、
  7 日に達すると直近 1 週間が窓の外に出るため絞り込みは失敗する。

### 症状: 予兆の節がいつも 0 件

- **Cause**: 2 通りある。(a) 予兆だけの銘柄がすべて条件 2（売買が活発）で落ちた——**正常**。
  標準エラーの「予兆が出た N 銘柄 → 売買が活発 0 件」で分かる。参考までに、2026-10-05 は予兆だけの
  7 銘柄のうち 3 銘柄が残った。(b) 台帳に予兆の記録が届いていない——「予兆が出た 0 銘柄」になる。
  台帳の同期が止まっている。
- **Solution**: `ls ~/dev/me/mcp-tradingview/data/paper-ledger` で最新のファイルが数日以内かを見る。
  新しければ (a) なので 0 件をそのまま報告する。古ければ (b) で、**同期の停止を先に直す**。
  どちらの場合も条件を緩めて予兆の銘柄を増やさない。

### 症状: 「判定できない技法の記録が N 件」と出る

- **Cause**: 台帳の記録のうち、完成か予兆か読み取れないものがある。`signal` が壊れている、または
  `any_of`（どれか 1 つ成立）の中に予兆の条件がある——後者は別の条件で記録された可能性があり、
  推測で振り分けない。
- **Solution**: **どちらにも数えていない**ことを報告する。記録は検証してから書かれるので通常は 0 件。
  出たら台帳の記録経路を調べる。

### 症状: 表の技法名が英字の slug のまま

- **Cause**: 該当する技法ノートに `title:` が無い、またはノートが削除された。
- **Solution**: `grep -L "^title:" ~/dev/me/mcp-invest-knowledge/sources/technique-notes/*.md` で
  題名の無いノートを特定する。**知識層側の欠落なので、そちらを直す。**

### 症状: 技法名の前後に `"` が付く

- **Cause**: 引用符を外す前のコードで判定している（image が古い）。2026-09-20 の実測では技法ノート 56 本中
  9 本が題名を引用符で囲んでいた（題名に `:` を含むため。いまの本数は [conditions.md](references/conditions.md) の数え方で出す）。
- **Solution**: image を作り直す。`screen.sh` は毎回作り直すので、`"` が出たら
  **古い image を使い回している合図**。並び順や該当判定そのものには影響しない。
