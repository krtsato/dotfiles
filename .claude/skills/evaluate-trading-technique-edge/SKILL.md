# 株式売買の技法に優位性があるかを同じ条件で測る

## CRITICAL: 先に読むこと

- **合流は分布を見てから測る。** `-levels` を勘で決めない。まず `-levels 1` で 1 回走らせ、
  `agreement_histogram` を読む。必ず [合意の水準](#合意の水準を決める) を読む。
- **「差が無い」を結果として受け取らない。** 比較が成立しているかを先に確かめる。
  付属の `compare.py` は項目が読めなければ**エラーで落ちる**。落ちたら直すまで報告しない。
- **基準（alpha 0.05）を結果を見てから動かさない。** 動かすなら測る前に決めて記録する。
- **「立証」と書かない。** 判定語は `outperformed_matched_null`（比較対象を上回った）まで。
- **q 値を必ず併記する。** p 値だけ見ると、29 個試して偶然 1 個当たったものを発見と呼んでしまう。

## 用語

| 正式名 | 意味 |
| --- | --- |
| 比較対象 | 売買回数・保有期間・銘柄を揃えた**でたらめな売買**（matched null）。入る日付だけが違う |
| p 値 | でたらめな売買 1000 通りのうち、技法以上だったものの割合 |
| q 値 | **同じ基準で拾った中に偽物が混じる割合**（多重検定の補正・BH-FDR） |
| 合流 | 複数の技法が同時に成立している状態。講義の「単独で使わない」に対応 |
| 合意の水準 k | 何個の技法が揃ったら候補とするか |
| 反対票 | 売り技法が成立していること。買い候補はこれが 0 のときだけ |
| 単調性 | 合意が増えるほど成績が上がるか。合流の本丸 |

## ユースケース

### 1. 指標を直したので測り直す

- **Trigger**: 「RSI を直したので影響を測って」「物差しを直した前後を比べて」
- **Steps**: 修正前後の実行ファイルを作る → 同じ cache・同じ種で両方走らせる → `compare.py`
- **Result**: 試行数・p 値・q 値・判定がどう動いたかの表。**判定が動かなくても入力が動いていれば書く**

### 2. 合流で評価する

- **Trigger**: 「合流で測って」「複数の技法を掛け合わせた場合は？」
- **Steps**: 水準を決める（下記）→ `-confluence-state` で走らせる → 単調性と各水準を読む
- **Result**: 合意が増えるほど成績が上がるかの判定と、水準ごとの表

### 3. 単独の技法を一通り測る

- **Trigger**: 「技法にエッジはある？」「一通り評価して」
- **Steps**: 既定の設定で走らせる → 判定の内訳を出す
- **Result**: 技法ごとの判定と、上回ったものの一覧

## 前提条件

| 要る物 | 確認方法 |
| --- | --- |
| mcp-tradingview | `ls ~/dev/me/mcp-tradingview/data/universe` |
| 技法ノート | `ls ~/dev/me/mcp-invest-knowledge/sources/technique-notes` |

## 手順

### ステップ 1: 実行ファイルを作る

**`go run` を使わない。** 背景で走らせると親が終わったときに扱いが不安定になり、
**出力が無いのに「終了」と見える**ことがある。先に実行ファイルにする。

前後を比べるときは、**枝ごとに別の名前で作る**。

```bash
cd ~/dev/me/mcp-tradingview
git worktree add .worktrees/before origin/main --detach      # 直す前
go build -o /tmp/study-before ./cmd/tradingview-signal-study  # ← .worktrees/before で
cd .worktrees/<直した枝> && go build -o /tmp/study-after ./cmd/tradingview-signal-study
```

**中身が違うことを必ず確かめる。** 同じなら比較になっていない。

```bash
md5 -q /tmp/study-before /tmp/study-after
```

1 回だけ測るなら `/tmp/study-after` だけでよい。

### ステップ 2: 走らせる

**cache と種を揃える。** これを揃えないと、差が修正由来か揺らぎ由来か分からない。

```bash
cd ~/dev/me/mcp-tradingview
/tmp/study-after \
  -universe data/universe/mvp-mixed.json \
  -notes-dir ~/dev/me/mcp-invest-knowledge/sources/technique-notes \
  -cache-dir /tmp/study-cache -seed 1 \
  -out-dir /tmp/out-after
```

合流も見るときは 2 つ足す。**`-levels` は必ず指定する**（既定は何も絞らない・次節）。

```bash
  -confluence-state -levels 4,5,6,7,8,9,10
```

20 銘柄で **15〜25 分**。背景で走らせ、**引数まで見て**二重起動を防ぐ。

```bash
ps aux | grep -E 'study-(before|after)' | grep -v grep
```

名前だけでは前後を区別できないので、**引数の `-out-dir` で見分ける**。

### ステップ 3: 突き合わせる

出力は `<out-dir>/<universe 名>-<実行日>.json` に 1 つできる。

```bash
ls /tmp/out-before /tmp/out-after        # ファイル名を確認する
python3 ~/.claude/skills/evaluate-trading-technique-edge/scripts/compare.py \
  /tmp/out-before/mvp-mixed-<日付>.json \
  /tmp/out-after/mvp-mixed-<日付>.json \
  technique                              # 合流なら confluence
```

**終了コードが 1 なら結果を読まない。** 比較が成立していないという意味で、
理由（項目が読めない・母集団が違う・関門が効いていない）が表示される。直してから測り直す。

## 合意の水準を決める

**勘で決めない。分布を見てから決める。**

### 分布を取る

まず水準 1 つだけで 1 回走らせ、`agreement_histogram` を読む。

```bash
/tmp/study-after ... -confluence-state -levels 1
```

```text
個数    バー数    割合      この数以上
  0    39,419   91.6%       100.0%
  1       436    1.0%         8.4%    ← ここで既に 1 割を切る
  6       233    0.5%         4.4%
 11       494    1.1%         2.2%
```

実測（日本大型 19 銘柄・2026-09-26）では **強気が 0 個のバーが 91.6%**。米国大型でも混合でも
形はほぼ同じで、**分布は母集団でなく技法の側の性質**で決まる。

### 水準は 4 つ以上並べる

**3 つでは足りない。** 単調性の判定は**検出力のある水準だけ**で行うので、低い水準が
検出力不足で落ちると**残り 2 点**の比較になる。**2 点は必ず単調に見える。**

実例（2026-09-26）: 水準 1/3/6 で「単調性が成立」と報告したが、9 と 12 を足すと崩れた。
**やらない場合**、偶然 2 点が並んだだけの形を「合意が効いている証拠」と読んでしまう。

### 試行数は水準に単調ではない

候補は「状態に**入った瞬間**」なので、**低い水準ほど状態が長く続き、入口はかえって少なくなる**。
実測では水準 1 で 50 件、水準 6 で 383 件、水準 12 で 87 件。**増減の向きだけで異常と判断しない。**

ただし**どの水準でも試行数が同一**なら、それは関門が効いていない合図（[Troubleshooting](#troubleshooting)）。

### 候補が少ないときは funnel を見る

「合意が稀」なのか「反対票が切っている」のかを**推測しない**。対処が逆になる。

| どこで落ちているか | 対処 |
| --- | --- |
| 合意の段階 | 銘柄を増やす・期間を延ばす |
| **反対票の関門** | 売りノート側を見直す（`dissent_share` で 1 本ずつの成立率が出る） |
| 地合いの関門 | 市場全体のゲートを確認する |

実測では**合意 3,635 バーのうち 198 バー（-95%）が反対票で落ちていた**。最大の寄与は 1 本で
**35.4%**（2 位の 6 倍）。原因はそのノートの `scope: market_regime` 宣言漏れで、個別銘柄に
市場全体の指標を当てていた。**「合意が稀だから」と読んでいたら永久に直らなかった。**

## 出力

表のあとに、**次の 5 点を必ず書く**。

1. **判定の内訳**（下の 4 語ごとの件数。前後で比べるなら両方。`compare.py` が出す）
   - `outperformed_matched_null` 比較対象を上回った
   - `not_significant` 上回ったとは言えない
   - `insufficient_power` 試行数や銘柄数が足りない
   - `not_evaluable` そもそも評価できない
2. **入力が動いたか**（試行数の変化。判定が動かなくても入力が動いていれば書く）
3. **q 値**（p 値だけ出さない。29 個試せば偶然 1 個は 0.05 を切る）
4. **合流の単調性**（合意が増えるほど成績が上がるか。合流を測ったときだけ）
5. **射程**（curated universe・生存者バイアス・手数料と滑りは入っていない）

### 入出力の例

**入力**: 「RSI を直したので影響を測って」

**出力**:

```text
判定: 前 有意でない 15 / 上回った 3     後 有意でない 14 / 上回った 3
入力: 6 技法で試行数が変化（最大 -24%）。ma-deviation-rate は p 0.889 → 0.063
q 値: ma-deviation-rate の q は 0.365（29 個の中では、まだありふれた数字）
射程: 20 銘柄・手数料と滑りを含まない
```

**入力**: 「合流で差が出なかったので終わり」

**出力**: 終わらない。**全水準で試行数が同じなら関門が効いていない**ので、水準を上げて測り直す。

## 成功基準

| 種類 | 基準 |
| --- | --- |
| **定量** | 測定の起動から報告まで **Bash 8 回以内**／価格の取得は cache がある限り **0 回**／`compare.py` の終了コードが **0**／同じ cache と種で 2 回走らせた結果が**完全に一致** |
| **定性** | 利用者が追加の指示を出さなくても、**判定の内訳・入力の変化・q 値・射程が揃っている**こと。「差が無い」と「測れていない」が読み分けられること |

## Troubleshooting

### どの水準でも試行数が同じ

**関門が効いていない。** `compare.py` は**注意書きとして報告する**（これだけでは落とさない）。
試行数の増減の向きは水準に単調でないので、**同じ数が並ぶこと**が合図になる。

原因は合意ではなく反対票の側にあることが多い。**`funnel` の `after_dissent` を見る**——
どの水準でも同じ数なら、売り技法が全バーで成立していて「合意」が結果に関与していない
（2026-09-26 の実例。どの水準でも 198 バーに潰れていた）。
この状態の結果は「差が無い」ではなく「**測れていない**」。

### `compare.py` が終了コード 1 で落ちる

**正しい動き。** 理由は 3 つのいずれかで、どれも「差が無い」ではなく「比較が成立していない」。

| 出るエラー | 意味 |
| --- | --- |
| 項目がありません | 存在しない項目名を比べると全件一致に見えるので、先に落としている |
| 比べる対象が揃っていません | 片側にしかない技法がある。universe かノートが違う |
| 水準を上げても試行数が減っていません | 関門が絞っていない |

### 出力ファイルができないのに「終了」と出る

`go run` を背景で走らせると起きる。**ログに読み込み完了までしか残らず、エラーも出ない。**
ステップ 1 のとおり実行ファイルにしてから走らせる。

### 同じ実行が二重に走っている

前の実行が生きているのに、確認コマンドが合致せず「終了」と読んだ場合に起きる。
`ps aux | grep study-bin` で**引数まで**見て数える。名前だけでは区別できない。

### `insufficient_power` と `not_evaluable` を混同しそう

| 判定語 | 意味 | データを増やせば解決するか |
| --- | --- | --- |
| `insufficient_power` | 試行数や銘柄数が足りない | **する** |
| `not_evaluable` | そもそも評価できない（スキャン専用の指標など） | **しない** |

混ぜると「もっとデータを集めれば結論が出る」と誤読させる。
